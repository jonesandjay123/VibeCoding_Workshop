# Session 10 Live Runbook

> 目標：把 IDE 遷移控制在暖身時間內，將主要課堂時間投入一個真正可用的人脈維護 Web App；任何單一模型、IDE 或網路失敗，主課仍能繼續。

## 推薦節奏：120 分鐘

| 時間 | 段落 | 學生要完成的事 | 老師要守住的事 |
| --- | --- | --- | --- |
| 0:00–0:05 | 開場與定錨 | 用自己的話說明想記住什麼、為何需要這個 App | 強調 IDE 只是暖身、產品才是主課 |
| 0:05–0:20 | 廈門環境 smoke test | 測 Antigravity；必要時切 TRAE 中國版 | 15 分鐘 timebox，不讓登入排障吞掉課程 |
| 0:20–0:35 | 需求訪談 | 說出日本客戶與廈大新朋友的兩種真實場景 | 把「做 CRM」縮成今天可驗收的一條工作流 |
| 0:35–0:50 | 資料建模 | 分辨 Person 與 Interaction | 不讓所有內容塞進一個大備註欄 |
| 0:50–1:00 | Payload contract | 用外部 LLM 整理一段虛構口述 | 要求只輸出 JSON、不補寫未知事實 |
| 1:00–1:05 | 短休息／轉場 | 選定實作用 IDE | 確認 repo、Node 與本機執行路徑 |
| 1:05–1:35 | Web MVP | 在 Agent 協助下完成最短主流程 | 每次只做一個可見、可驗收的小改動 |
| 1:35–1:50 | End-to-end 驗收 | 口述 → payload → 預覽 → 修正 → 建檔 | 特別測不完整日期、未知欄位與錯誤 JSON |
| 1:50–2:00 | 回顧與 Git | 說出 AI、Agent IDE、App 各自的角色 | 看 diff、local run、commit；不臨時擴功能 |

## 開場講法

```text
今天我們會先確認妳在廈門還能用什麼 AI 開發工具，
但這只是十五分鐘的暖身。

今天真正要做的是妳剛剛提出的人脈記憶庫：
不是讓 AI 自己決定誰是什麼樣的人，
而是讓妳很快說出一次相遇，請任何可用的 AI 幫忙整理，
最後由妳確認後，放進自己的 App。

今天的成果不是完整 CRM，而是跑通一次真實、可重複的紀錄流程。
```

## A. IDE 暖身：最多 15 分鐘

### Antigravity smoke test

- [ ] 不登出、不重裝，直接用她在廈門的日常網路。
- [ ] 開啟既有、沒有 secrets 的小 repo。
- [ ] 連續兩次請 Agent 用一句話摘要 README，不修改檔案。
- [ ] 請它說出啟動指令與一個最小修改會涉及的檔案。
- [ ] 只改一行無風險 UI 文案，查看 diff。
- [ ] 執行原本已有的本機指令。

核心請求連續失敗兩次，就把 Antigravity 判為 international optional layer，不再現場修帳號或網路。

### TRAE 中國版 smoke test

用完全相同的 repo 與任務測試：

```text
先閱讀 README 和 package.json，不要修改。
告訴我正確的啟動指令，以及若只改一行首頁文字，最少需要修改哪些檔案。
等我確認後再修改；不要安裝套件、不要更改部署設定，也不要接觸 secrets。
完成後顯示 diff，並執行原本已有的安全檢查或啟動指令。
```

通過標準：能登入、讀 repo、提出最小修改、顯示 diff、執行本機指令。TRAE 的 `Auto` 背後可能動態選模；Google 登入也不代表使用 Gemini，本堂不花時間猜測路由模型。

### IDE 都失敗時

立即回到 VS Code 或任何已能工作的 editor。外部 LLM 仍可協助產生規格與 payload；Web App 也可由學生手動修改。課程主題不依賴特定 agent。

## B. 需求訪談：只問能改變資料設計的問題

不要從「妳想要什麼功能？」開始。依序問：

1. 見到日本舊客戶前，妳最希望快速想起哪三件事？
2. 在廈大認識一個新朋友後，隔天最容易忘記什麼？
3. 哪些資訊屬於這個人，哪些只屬於某一次見面？
4. 下一次聯絡前，App 應該幫妳看到什麼？
5. 哪些資料即使 AI 能整理，妳也不想保存？

把回答收斂成兩個使用故事：

```text
作為維繫日本客戶的人，
我希望在再次聯絡前快速回看對方的偏好與歷次互動，
以便延續真正相關的話題，而不是重新從零認識。

作為剛到廈門大學的學生，
我希望每次認識新朋友後快速留下相遇脈絡與下一步，
以免因為生活忙碌而忘記重要細節或答應過的事。
```

## C. 資料建模：Person 與 Interaction 分開

### Person：相對穩定

- 顯示名稱
- 關係分類
- 組織／角色
- 地點、語言、標籤
- 經本人確認的穩定偏好或背景

### Interaction：可以持續新增

- 日期、場合與管道
- 互動摘要
- 對方親口提到的事情
- 自己的觀察
- 雙方答應的事項
- 下次行動與追蹤日期

若學生想把所有內容放在 `notes`，用這個問題帶回來：

> 三個月後再次見面時，妳想看到一大段舊文字，還是一條按日期排列、可以快速回想的互動時間軸？

## D. Payload contract 實驗

使用 [`payload-contract.md`](./payload-contract.md) 的 prompt。先讓一個可用的外部 LLM 處理一段虛構口述，再人工檢查：

- [ ] 沒有把未知日期補成完整日期。
- [ ] 沒有虛構姓名、地點或關係。
- [ ] 「對方說過」與「我的觀察」有分開。
- [ ] 可能的下次話題沒有被存成事實。
- [ ] 回傳的是可解析 JSON，沒有 Markdown code fence 或額外說明。

若有時間，可把同一段口述交給第二個 LLM。比較重點不是哪個更會寫，而是哪個更遵守同一份 contract。

## E. Web MVP 實作節奏

一次只交付一個垂直切片：

1. 先顯示兩位虛構人物與各自互動紀錄。
2. 再完成「貼入 payload → 解析 → 預覽」。
3. 再加入人工修正與確認建檔。
4. 最後保存到本機並測重新整理。

搜尋、提醒、動畫、深色模式與視覺精修都是 stretch goals。若前四步尚未走通，不開始 stretch goal。

### 每一小步的 Agent 節奏

```text
先說明目標與驗收條件
→ 要求 Agent 先列出會修改的檔案
→ 限制一次只做一個垂直切片
→ 查看 diff
→ 在 localhost 親眼驗收
→ 成功才進下一步
```

## F. End-to-end 驗收案例

使用虛構資料口述：

```text
我今天在廈門一場市集認識一位大家叫冰淇淋大哥的人。
他經營一家冰淇淋店，也提到家裡有一名年幼的小孩。
我們聊了廈門的餐飲創業，還一起去了附近的展覽。
我答應下週把一篇日本甜點趨勢的文章傳給他。
我不確定他的本名和店名，也不記得孩子生日的完整日期。
```

必測情境：

- 不完整資訊保持 `null`，不能由 AI 猜測。
- App 能顯示 `requiresReview`。
- 學生可以在存檔前修改。
- 同一人物的第二次 payload 能加入互動，而不是靜默建立重複人物。
- 錯誤 JSON 顯示可理解的錯誤，不造成整個頁面崩潰。
- 重新整理後仍能找到人物與互動。

## 三條現場分流

### Route A：Antigravity 與 TRAE 都可用

選她最願意每天打開的一個作本堂 primary，另一個只記為 fallback。不要重複做兩次完整實作。

### Route B：只有一個 IDE 可用

直接用它完成主課。工具比較到此停止。

### Route C：Agentic IDE 全部不可用

使用 VS Code 加外部 LLM：LLM 提供單步修改建議，學生手動貼入並執行。仍然可以完成 payload contract 與 Web MVP 的核心學習目標。

## 不要踩的坑

- 不把安裝、登入或猜模型拖成主課。
- 不一開始就說「幫我做完整 CRM」。
- 不把人物與所有互動壓成一個不可追蹤的大備註欄。
- 不讓 LLM 回傳 Markdown、散文與 JSON 混合內容。
- 不把 AI 建議的聊天話題寫進已確認事實。
- 不使用真實客戶資料測試，也不把 `.env`、token 或私人檔案交給 Agent。
- 不因 localStorage demo 成功，就宣稱資料已足以安全長期保存。
- 不在課末臨時加入雲端、通知、PWA 或 iOS。

## 收尾問題

```text
今天真正幫妳完成工作的是哪一層：模型、Agent IDE，還是妳自己定義的資料格式？
如果明天不能使用今天的 LLM，這個 App 還能不能繼續工作？
剛才哪一項 AI 整理需要妳修正？
日本客戶與廈大朋友的紀錄，哪些欄位相同、哪些應該不同？
這個 prototype 要到什麼程度，妳才願意真的每天使用？
```

## 課後再決定，不在現場展開

- 搜尋與標籤篩選
- 待追蹤清單與提醒
- JSON 匯出／匯入與備份
- PWA 手機安裝
- 更可靠的本機資料庫
- 經明確選取資料後才產生的日文／中文問候草稿
- iOS 原生版是否值得開發
